# 个人交易事件动态日历 Roadmap

## 1. Roadmap 目标

本目录把产品需求拆成可以逐项执行、验证和复盘的开发计划。执行原则是：

1. 先保证事件数据模型正确，再开发自动抓取；
2. 先形成可用的人工日历，再接入外部来源；
3. 先保证来源可追溯、变更可识别，再扩大覆盖范围；
4. 先保证提醒不重复、失败可见，再增加更多提醒渠道；
5. 每完成一个阶段，都必须在对应文档末尾填写“完成情况与质量补充”。

## 3. 总体阶段安排

| 阶段 | 建议周期 | 进入条件 | 退出目标 | 初始状态 |
|---|---:|---|---|---|
| Phase 0 | 1 周 | 产品文档已确认 | 范围、来源、分类和线框图冻结 | 有条件通过 |
| Phase 1 | 1 周 | Phase 0 通过 | 工程、数据库和容器可运行 | 已完成 |
| Phase 2 | 1 周 | 数据模型稳定 | 人工事件闭环可用 | 已完成 |
| Phase 3 | 2 周 | 事件 API 可用 | 日历主要页面可用 | 进行中 |
| Phase 4 | 2～3 周 | 人工事件闭环稳定 | 核心官方来源可自动同步 | 进行中 |
| Phase 5 | 1 周 | 变更识别稳定 | 提醒和 ICS 可可靠运行 | 进行中 |
| Phase 6 | 1 周 | 核心业务闭环完成 | 可安全部署、监控和恢复 | 未开始 |
| Phase 7 | 2 周开发验收 + 30 天观察 | 部署环境就绪 | MVP 正式通过验收 | 未开始 |
| V1.1 | 4～6 周 | MVP 稳定 | 动态发现和人工审核闭环 | 待规划 |
| V1.2 | 4～6 周 | V1.1 稳定 | 交易专项数据得到增强 | 待规划 |

全职单人开发预计 10～12 周形成 MVP，随后进行 30 天稳定性观察。业余时间开发应按 16～20 周安排。

## 4. 执行规则

### 开始阶段前

- 检查前置阶段是否通过质量门；
- 把本阶段状态改为“进行中”；
- 确认依赖、账号、数据源和测试样本已经准备；
- 若范围变化，先更新 `13_执行状态与变更日志.md`。

### 阶段进行中

- 按任务复选框推进；
- 每个重要功能同时补充测试；
- 发现超出范围的需求时进入后续版本，不直接插入当前阶段；
- 所有架构决策、数据源替换和延期原因都要记录。

### 阶段完成后

- 执行阶段文档中的验收测试；
- 填写文档末尾的“完成情况与质量补充”；
- 按统一质量规范评分；
- 更新总状态和变更日志；
- 只有结论为“通过”或“有条件通过”时，才能进入下一阶段。

## 5. 状态定义

```text
未开始：尚未投入开发
进行中：正在实现或验证
受阻：存在无法继续的外部依赖
待验收：实现完成，尚未通过质量检查
有条件通过：核心目标达成，存在已记录的非阻断问题
已完成：全部验收标准通过
暂停：主动停止，等待范围或资源调整
```

## 6. MVP 最终完成标准

- 核心市场事件能够自动同步；
- 同一事件多来源不会重复展示；
- 改期、取消和时间补充有完整历史；
- 所有事件都有来源和最后核验时间；
- 只有日期的事件不会被伪造具体时间；
- 人工锁定字段不会被自动同步覆盖；
- 飞书提醒不重复，失败可以重试；
- 数据源失败和 Worker 停止不会静默；
- 数据库能够每日备份并完成恢复演练；
- 系统通过 30 天稳定性观察。
